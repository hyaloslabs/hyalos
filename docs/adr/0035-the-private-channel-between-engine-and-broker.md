# ADR-0035: The private channel between the engine and the broker

**Status:** Accepted; `start_job` gains the job's socket path in wire version 2 ([ADR-0038](0038-model-calls-from-the-sandbox-and-the-provider-key-file.md)), and the job's forge token in wire version 3 ([ADR-0044](0044-minting-per-job-github-tokens-from-the-app.md)); wire version 4 adds `read_issue` and `issue`, the one message whose fields hold forge-authored text, as capped `ForgeText` ([ADR-0047](0047-forge-content-as-typed-values-and-derived-taint.md))

## Context

[ADR-0002](0002-one-binary-two-processes-sandboxes.md) decides that one `hyalos` binary runs as the engine and launches itself as the broker, and that the engine receives only typed values over its own trusted channel, never model text or raw forge content. [ADR-0004](0004-one-signed-manifest-per-job.md) decides that the broker enforces a manifest the engine signed and nothing else, and [ADR-0022](0022-engine-keys-generation-storage-backup-and-loss.md) that the manifest key is ephemeral and the broker gets only its public half. [ADR-0031](0031-the-signed-manifest-and-its-admission.md) builds the check. They leave how the engine starts the broker, what the channel is, who may use it and what may cross. This ADR adds them for story S3.11. It changes nothing those ADRs decided.

## Decision

**The channel is a Unix socket in a directory only the engine's user can enter.** The engine makes a directory inside the runtime directory (mode 0700, a name drawn from the operating system, refused if it exists), listens on a socket in it (mode 0600), and starts the broker with the socket's path. It accepts one connection and checks with the kernel who is on the other end (`SO_PEERCRED`: process id and user id, which the peer cannot choose). Only the process it started, as the same user, is accepted. Any other connection is closed unread and noted, and the engine goes on waiting. When the broker has connected, the engine stops listening and removes the socket and directory, so there is nothing left to connect to. The broker checks the other way: the process that answers must be its own parent and the same user, or it sends nothing and exits. On a system without peer credentials the channel does not open. The alternative, a socket pair handed to the child, would leave no path to connect to at all, but it gives no way to show that another peer is refused, and the story asks for that to be shown.

**The broker is the same executable.** `hyalos broker <socket>` is started by the engine with an empty environment and standard input and output on `/dev/null`, and refuses to run under any other parent. The engine draws a fresh manifest key from the operating system for each run and keeps it in memory. The broker gets the public half in the first message, over the channel, which is the only place it can come from.

**Messages are a closed set of typed values.** A frame is a four-byte big-endian length (at most 64 KiB, checked before anything is read) and JSON. `ToBroker` is `hello` (protocol version and the manifest public key), `start_job` (job, role, the signed manifest's envelope in hex), `end_job` and `shutdown`. `ToEngine` is `ready`, `admitted`, `refused` (job and a `ReasonCode`) and `gate` (job, gate, digest of the inputs, answer and a reason code), which is the one fact the broker reports that the engine records ([ADR-0024](0024-event-origins-and-time-order.md)). There is no string field that is not a reason code (lowercase letters, digits and `.`, `_`, `-`, at most 64 bytes), no map, no list, no free field. A frame with a field the type does not name, a variant the direction does not have, a value of the wrong type, a reason that is not a code, more than one message, or an oversize length is refused whole. The refusal names the kind of fault and nothing from the frame.

**A bad frame from the broker ends the channel.** The engine does not go on talking to a broker that has sent it something that is not a message: it closes the channel and stops the process. Further sends fail. Dropping the handle stops the broker; the broker exits when the channel closes.

**The broker keeps what the engine tells it.** A job is live from `start_job` to `end_job`. `start_job` carries the role the credential will have, and admission checks it against the signed manifest as [ADR-0031](0031-the-signed-manifest-and-its-admission.md) says. A refused manifest fails that job and not the broker. A job started twice is refused the second time and the first stands. The broker's clock is the system's, and one that cannot read it reads as the end of time, so every deadline has passed.

## Consequences

Another process of the same user that connects first is refused and cannot read or write the channel, and nothing can connect after the broker has. The engine can only be given typed values by the broker, so a compromised broker cannot put model text, a prompt or a page into the engine through this channel, only choose among the values the types allow. What it can do is send false typed values (a wrong gate answer); the engine checks those against its state when it records them, which the gate story does. A same-user attacker who can attach to the engine's process is outside this channel's protection (the engine is marked not dumpable, [ADR-0030](0030-hardening-the-engines-key-owner-and-core-dumps.md)).

The `hyalos` package becomes a library and a binary so the launcher and channel can be tested directly. Not here: the gate flow that turns a `gate` message into an event, the per-job credentials the broker issues to sandboxes, the sandbox-facing socket, and a command that starts the engine and calls `BrokerProcess::launch_self`.
