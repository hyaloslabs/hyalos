# Hyalos

Clean-room Rust rewrite of hivrr. Currently moving from planning into the first code. The Cargo workspace skeleton and CI exist but the crates are empty. Throwaway spike rigs under `spikes/` are not part of the workspace and not trusted core.

## Documentation rules (see docs/README.md)

- Intent and scope: `docs/prd/`. Never put status there.
- Decisions: `docs/adr/NNNN-title.md`, one per file, from `0000-template.md`. Add new rows to `docs/adr/README.md`.
- Never edit Context, Decision or Consequences of an **Accepted** ADR. Write a new ADR that supersedes it and change only the old one's Status line. **Proposed** ADRs may be edited.
- Status lives in GitHub issues (epics as parent issues, milestones M1 to M4), not in this repo. `docs/planning/` is working material only.

## Planned stack (ADR-0001)

Single Cargo workspace producing one `hyalos` binary (engine + broker). Trusted-core paths require human code-owner review.

## Code layout (ADR-0017)

- `core/` is the trusted core: code that runs in the engine or broker process. It has a 30,000-line budget.
- `crates/` holds everything else (`xtask` checks, later the simulator and test kits). It is not counted.
- Before pushing, run what CI runs: `cargo fmt --all --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, `cargo test --workspace --locked`, `cargo xtask layout`, `cargo xtask lines`. The toolchain is pinned in `rust-toolchain.toml`.
- `hyalos-types`, `hyalos-log`, `hyalos-policy` and `hyalos-engine` are deterministic (ADR-0013). They get time from `hyalos_types::Clock` and randomness from `hyalos_types::Entropy`, never from the system. Their identical `clippy.toml` bans `SystemTime`, `Instant`, `HashMap`, `HashSet`, `RandomState` and `fs::read_dir`, and they may take no external dependency without an entry in `EXTERNAL_ALLOWED` in `crates/xtask`.
- The event log is `hyalos-log` (ADR-0018): SQLite, hash-chained, Ed25519-signed. Check one with `hyalos log verify`: it reads `events.db` from the data directory and the public key from `engine.pub` in the config directory (`$HYALOS_DATA_DIR` / `$HYALOS_CONFIG_DIR`, else XDG, else `~/.local/share/hyalos` and `~/.config/hyalos`); `--db`, `--public-key`, `--public-key-file` and `--expect-head <seq>:<hash>` override or add to that. The public key must never come from the log itself. Only the engine depends on `hyalos-log`; the broker must not.
- Events are the closed `hyalos_types::Event` set (ADR-0019), stored as tagged JSON. Tasks, jobs and holds are an in-memory `State` that `hyalos-engine` rebuilds by replaying the log; `Engine::submit` checks an event against the state before it appends, so the log never holds an event replay would refuse. An id is the sequence number of the event that created it.
- Schema versions (ADR-0023): the log is never rewritten, so an event written at an older version is upcast in memory when read (`Event::decode_with` and a `hyalos_types::Schema` of pure per-kind steps), and new events are written at `Schema::current`. A newer version than the build knows is refused, never skipped. Bumping `SCHEMA_VERSION` means adding the new version's pinned payloads (`core/types/tests/schema.rs`) and the steps; `Engine::open_with` runs another schema against a past log.
- Origins and time (ADR-0024): the broker may submit only `gate.answered` (`Event::may_come_from`); every other kind is the engine's, and `Engine::rule_gate` records an unknown answer's job-ending and hold as engine events. `submit_all` takes `(Origin, Event)` pairs. An event stamped earlier than the one before it is refused (`TimeWentBackwards`), and replay refuses both violations. `Engine::open` has no exists-then-open step: it opens, then verifies that same open file with `Log::verify`.
- Releasing a hold (ADR-0025): `hold.opened` records `Stakes` (tier plus sensitive categories, set by the engine on `GateRequest`); `Stakes::may_be_resolved_by` is the one authority table (a human may release anything; touching credentials, policy, publishing or a capability grant needs a human). A hold is released only by `Engine::reevaluate_hold` (a fresh on-time allow for its own gate and inputs; anything else writes nothing) or `Engine::decide_hold` (policy, verifier or human, with a `ReasonCode`); `submit` refuses `hold.resolved`. Schema version 2 added this (old holds read as irreversible).
- Compaction (ADR-0026): `hyalos log compact` archives every event to a read-only verified file and leaves a signed snapshot in the `anchors` table (state as a versioned `hyalos_types::StateImage`, signed under its own tag, chained to the previous snapshot); no event or hash changes, and the log is format version 2 afterwards. `Engine::open` starts from the latest snapshot and replays only what follows, and `Engine::compact` snapshots a state only after checking it against a replay. `hyalos log verify --archive <file>` checks archives against the snapshots; without them the history before the latest snapshot rests on the engine's signature. `hyalos log prune <archive> --yes` is the only thing that removes history. Procedure: `docs/operations/log-compaction.md`.
- Recording a prune (ADR-0027): `hyalos log prune` needs the engine's key and the engine stopped; it writes an engine-only `archive.pruned` event (`last_seq`, `last_hash` of the archive's last event) through `Engine::record_prune`, which refuses unless a snapshot of this log stands exactly there, and only then deletes the file, so a re-run after a crash records nothing twice. The list lives in the state (`State::pruned`, `StateImage` version 2, a version 1 image reads as none), so compaction keeps it; `hyalos_engine::pruned_archives` lists it from the public key alone and `verify` prints it. Schema version is 3 (`archive.pruned` only; no payload changed).
- Auditing snapshots (ADR-0028): `hyalos log audit [--archive <file>]...` replays the archives and the log from event 1 (`hyalos_engine::audit`) and compares the state at each snapshot with the one it carries, naming the first differing field (`StateImage::first_difference`); public key only, read-only. Exit 0 only if every snapshot was compared and matched, 1 on a difference or a file that does not check out, 3 if the archives given leave a snapshot uncompared (never a pass). `verify` shows a snapshot is the engine's; `audit` shows it is right.
- Cancelling and refusals (ADR-0029): `Engine::cancel_task` writes `task.cancelled` (who decided, a `ReasonCode`) for a held task; the state allows it only to a decider `Stakes::may_be_cancelled_by` permits at every open hold (the release table without a fresh gate allow), and the task then has no open holds, takes no job, completion or hold, and its holds stay unresolved (`State::hold_is_open` is false). A gate answering deny when a hold is asked again is recorded as `hold.refused` (`Reevaluation::Refused`) and changes no state; a refusal alone never ends a task and a later allow still releases. `submit` refuses both raw. Schema version is 4 and `StateImage` version 3.
- Policy errors (ADR-0008, S3.15): `hyalos_policy::Policies::judge` is the only way to ask Cedar. Cedar skips a policy that errors and reports it only in the diagnostics, so `judge` checks the diagnostics first and any error at all is `Unknown` (reason `policy.error`; an unbuildable question is `policy.bad_request`), never `Allow` and not `Deny`; `Allow` needs a clean evaluation. Cedar's types stay inside `core/policy/src/cedar.rs` (callers pass text and get a `Verdict`). `cedar-policy` is in `EXTERNAL_ALLOWED` with default features off (it still turns on `serde_json`'s `preserve_order` for the whole build, so nothing may rely on a `serde_json` map's key order: `StateImage::first_difference` sorts its keys), and `deny.toml` allows `Apache-2.0 WITH LLVM-exception` for its build dependency `ar_archive_writer`. Not built yet, left on S3.15 (#100): the `cedar-policy-symcc` CI proof over the baseline (needs the baseline and schema of S3.6, #21) and holding requests that depend on a stored operator policy that stopped validating (needs stored policies).
- The signed manifest (ADR-0031): `hyalos_types::Manifest` (version 1; sorted sets, so the same bytes every time) is signed by `ManifestKey::sign` as Ed25519 over the tag `hyalos.manifest.signature`, the version (4 big-endian bytes) and the JSON; `SignedManifest::open` checks version, then signature, then parses, and refuses a document whose own version differs. `hyalos_broker::Admission::admit` also checks the credential's job, `LiveJobs`, the credential's role and the deadline (valid at the deadline, expired after). Types and both keys are in `hyalos-types` so the engine and broker share them without depending on each other. Nothing generates a manifest key yet. Pinned bytes and signature are in `core/types/tests/manifest.rs`.
- Substrates (ADR-0032): `hyalos_substrate::{Substrate, Sandbox, SandboxSpec}`; a spec has no field for network, host mounts or privileges, `SandboxSpec::validate` is the one place a bad spec is refused, and the broker socket is always at `BROKER_SOCKET_IN_SANDBOX`. `ContainerSubstrate` drives `podman`/`docker` with `--init` (the runtime's init is PID 1 and reaps orphans, ADR-0041; Podman needs `catatonit`), `--network none`, read-only root, user 65534, no caps, no new privileges and limits. Every driver must pass `hyalos_substrate_contract::run` (`crates/substrate-contract`; behaviour for all, isolation for any driver that claims it, skips listed in the report); `LocalProcessSubstrate` is the fake. The container test skips without a runtime unless `HYALOS_REQUIRE_CONTAINER` is set (CI sets it).
- The shipped policy (ADR-0033): `core/policy/policies/{schema.cedarschema,baseline.cedar}` are included in the binary. `Policies::load(operator)` adds operator policy (ids `operator.N`, no templates) to the five `baseline.*` forbids and validates the lot against the schema; `judge_request(&PolicyRequest)` takes typed facts (`Action`, `JobFacts`, `TargetFacts`, `approved`, `subscription_token`). Each action is in exactly one tier group (`Action::tier`, kept equal to the schema by a test). `crates/policy-proof` (not core, never linked into the binary) proves the baseline with `cedar-policy-symcc` and cvc5 1.3.1 in the CI job `policy proofs`, and `policy-diff <old>` reports whether a change allows more; its tests skip without `cvc5` unless `HYALOS_REQUIRE_CVC5` is set. `cedar-policy` is pinned `=4.14.1` to match symcc `=0.8.1`.
- The policy store (ADR-0034): the operator's Cedar policy is the latest `policy.approved` event (the whole document, `by`, a `ReasonCode`; schema version 5, `StateImage` version 4 keeps it as `PolicyImage`). `Engine::approve_policy` is the only way to write it; `submit` refuses the raw event, the broker may not send it, and the state refuses any decider but a human (the ADR-0025 table for an irreversible action touching policy; the human claim is the caller's, as for holds, with signatures in S5.4) and a document over `MAX_POLICY_DOCUMENT` (256 KiB). It loads the document with `Policies::load` first and writes nothing if that fails (`Engine::check_policy` asks without writing). `Engine::policies` is the baseline plus the policy in force; if the stored document no longer validates it returns `PolicyUnavailable` and `mint_manifest` holds with `policy.invalid`, never allows (this is the last box of S3.15, #100). `Engine::mint_manifest` (`core/engine/src/mint.rs`) signs only for a running job with a future deadline and only if the policy allows every action, tool, data flow and host in it, one question each, never setting `approved` (so no irreversible action mints until S5.4); it writes nothing. The schema gained `Job.budget_tokens`, `Target.name` and the routine actions `use_tool` and `data_flow` (12 actions).
- The engine-broker channel (ADR-0035): `hyalos_types::wire` is the closed set of messages (`ToBroker`: hello with the manifest public key, start_job, end_job, shutdown; `ToEngine`: ready, admitted, refused, gate), framed as a 4-byte length (cap 64 KiB, checked before reading) and JSON with `deny_unknown_fields`; the only string a broker can send is a `ReasonCode`, and a frame that is anything else is `WireError::Malformed` without echoing it. `hyalos_broker::serve`/`Broker` is the broker's side (live jobs come only from the engine; a refused manifest fails the job, a bad frame ends the channel). The `hyalos` package is now a library plus the binary: `channel::Listener` (0700 directory, 0600 socket, accepts only the started pid and the same uid by `SO_PEERCRED`, closes others unread) and `launch::BrokerProcess::{launch, launch_with, launch_self, start}` (broker is `hyalos broker <socket>`, empty environment, stdin/stdout `/dev/null`; a bad frame from the broker closes the channel and kills it; dropping it stops it); `fresh_manifest_key` draws the per-run manifest key. `launch_self` has no caller yet: no command starts the engine.
- Model protocols (ADR-0037, S3.8): `hyalos_broker::model::Relay` serves every model call through an `Adapter` (`Anthropic`, `OpenAi`: paths, credential header, header allowlist, which tools the harness runs, retryable status 529/503, error shape) and a `Transport`. Order: unknown path or non-POST 404, a path with a space or control character or a passed-on header with a control character 400, over 32 MiB 413, not a JSON object 400, `background` 400, a reader with any tool or MCP server 403 `model.reader_tools`, a spent budget 402 `budget.spent` (counting tokens is free), then hosted tools are removed by allowlist (exact types; unknown ones too) and the key added. Upstream 429/502/503/504/529 and `TransportError::UNREACHABLE` (nothing sent) are retried (4 calls, `retry-after` or 1/2/4 s, cap 30 s) then answered 529/503, never 429; any other transport error is 502 at once (the provider may have generated); OpenAI `insufficient_quota` is 402. `Meter` charges the job the usage a successful generation reports, when the body ends or is dropped, and fails closed: no usage, or usage not read in full, charges the whole budget. `HttpTransport` is plain HTTP to loopback only, or TLS to any host (ADR-0039). `core/broker/src/model` has a 1,200-line budget in `PART_BUDGETS` (`cargo xtask lines`). The contract suite is `core/broker/tests/model.rs`. Not wired into the broker yet (S3.2).
- Model calls from the sandbox (ADR-0038, S3.2): the broker reads `provider.keys` (config dir; `anthropic.key`, `anthropic.base`, `openai.key`, `openai.base`; owner-only, checked by `keys::read_private` like `engine.key`) itself: `hyalos broker <socket> [<provider.keys>]`, `BrokerProcess::launch_with`/`launch_self(.., provider_keys, ..)`. A missing file means calls get 403 `model.no_provider`; an unsafe or bad one stops the broker. Each job has its own socket: the engine makes `launch::JobDir` (random name, 0711) and sends `JobDir::socket()` in `ToBroker::StartJob { socket }` (wire version 2, never on the command line); on admission the broker listens there (0666) with `hyalos_broker::sandbox` (one HTTP/1.1 call per connection, `content-length` bodies only, 16 calls at once, `/v1/messages*` to Anthropic and `/v1/responses*` to OpenAI, past the deadline 403 `admission.expired`), and `end_job` removes it and forgets the meter. A generation holds its output limit (default 16,384) capped to the budget left and is rewritten to ask for no more; spent is 402 `budget.spent`, held by calls in flight is 529/503 `budget.held`. `core/hyalos/tests/model_call.rs` runs the real broker and a local-process sandbox and scans its environment, files and memory dump for the key. Operator procedure: `docs/operations/provider-keys.md`.
- TLS to providers (ADR-0039, S3.15b): `HttpTransport::new` takes `https://host[:port]` (rustls on `ring`, TLS 1.3 and 1.2, the compiled-in `webpki-roots` Mozilla set) or `http://` loopback. Nothing in configuration touches TLS; `with_roots_der` (other roots) is for tests only and called from code. The handshake and certificate check finish before the request is written; a TLS failure is `transport.tls_refused` (502 `provider.tls_refused` at once, not retried), a network failure in the handshake `transport.unreachable` (retried); connect and handshake have 30 s each. `deny.toml` allows `ISC` (ring, rustls-webpki, untrusted) and `CDLA-Permissive-2.0` (webpki-roots). Tests: `core/broker/tests/model_tls.rs` with a test authority in `tests/fixtures/tls` whose private key was discarded.
- The sandbox image (ADR-0040, S2.9): `images/sandbox/Containerfile`, built from the repository root (`docker build -f images/sandbox/Containerfile [--target test] .`). Harnesses pinned in `images/sandbox/harness/package.json` and its lockfile (regenerate the lock with the image's own npm, not the host's); base images pinned by digest. `crates/sandbox-tools` (not core, standard library only) has `hyalos-forward <program> [<args>...]` (makes `$HOME`/`$CODEX_HOME`, relays `127.0.0.1:8089` to `/run/broker.sock`, runs the harness), `hyalos-submit` (posts to `/hyalos/submit`; the broker answers 404 until S4.7) and the test-only `hyalos-dns-log` (UDP and TCP). The image sets every ADR-0016 setting in `ENV`, `/etc/hyalos/codex/config.toml` and `/etc/claude-code/managed-settings.json`. `crates/sandbox-tools/tests/image.rs` runs each harness under the substrate's isolation against the real broker and a scripted model and checks the DNS log and every request on the channel (a proxied harness makes no lookup, so both are needed), with three controls (Codex's analytics on the channel and in DNS, Claude Code's non-essential traffic on the channel, ADR-0041); it skips without the `hyalos-sandbox:test` image unless `HYALOS_REQUIRE_SANDBOX_IMAGE` is set, which the `sandbox image` workflow does when the image, tools, broker, types or lockfile change. `JobDir::create` refuses a runtime dir that makes the socket longer than `wire::MAX_SOCKET_PATH` (100).
- Egress (ADR-0042, S3.5): on a job's socket a `CONNECT host:443` or an absolute `http://` request is a proxy request for the egress gate (`hyalos_broker::egress`); a path is a model call. Allowed only if the job is live and in its deadline, the target is a host name (IP literals and numeric forms always refused), the port is 443 for CONNECT or 80 for HTTP, the host is in `manifest.egress_hosts` and not a provider API host (`egress::NEVER`), and it resolves to a public address (`PublicResolver`; `Egress::with_resolver` is for tests, from code only). A refusal is 403 plus `ToEngine::Gate { gate: egress, answer: deny, inputs: SHA-256 of host:port }` sent unprompted (once per distinct refusal, 32 per job, then `egress.too_many_refusals`); `serve_with` writes every frame from one writer thread (`W: Send`), and `Broker::report_to` sets where reports go. `crates/sandbox-tools/tests/egress.rs` runs Claude Code's web fetch and Codex's `curl` against `allowed.hyalos.test` (a loopback HTTPS server, test CA in `crates/sandbox-tools/tests/fixtures/tls`, key discarded) and an unlisted host, with a control for `skipWebFetchPreflight`; shared helpers are in `tests/common/mod.rs`. The image's `test` target installs curl from the pinned Debian snapshot (apt bypasses the image's proxy variables).
- Choosing the substrate (ADR-0043, S2.3): `job.started` names its `substrate` (`hyalos_types::SubstrateName`, short-code grammar; schema version 6, an older one reads as `unrecorded`; the state does not keep it). `Substrate::recorded_as` (container: `container.podman`/`container.docker`) and `Substrate::ready(image)` (container: answers, has the image, and starts `true` under `--init` with the sandbox's options, leaving nothing). `hyalos_substrate::choose(os, drivers, image)` refuses a host that is not Linux before asking any driver (`Unsupported`), then picks the ready driver with the strongest isolation (first among equals) and reports every one tried; `detect(image)` is that on this host for Podman then Docker. `hyalos doctor [--image <image>]` (default `hyalos-sandbox:latest`) prints host, each substrate, the one chosen and the provider spend-cap reminder; exit 0 ready, 1 not, 2 usage. Nothing starts a job yet (#70).
- GitHub tokens (ADR-0044, S3.9, S3.4): `hyalos::github::GitHubApp` (engine process, `hyalos` crate) reads `github.app` (`app_id`, optional `api`; a name with `token` or `pat` is refused) and `github-app.pem` (`keys::read_private`) from the config dir, signs an RS256 JWT with `ring` (not the `rsa` crate, RUSTSEC-2023-0071), finds the installation on the manifest's repo and mints a token for that one repo with `permissions_for(actions)` (the table in the ADR; `publish`, `change_policy`, `export_credentials` and unknown names refused; no forge action means no token and no call), then refuses and revokes a grant wider than asked. `revoke` at job end. `ToBroker::StartJob` carries `forge_token: Option<ForgeToken>` (`hyalos_types`, `Debug` hides it, up to 4,096 characters since GitHub's are about 400, ADR-0045; wire version 3); once GitHub has issued a token, every refusal revokes it; the broker keeps it per admitted job (`Broker::forge_token`) and drops it at `end_job`. `HttpTransport::request(method, ..)` takes `GET`/`POST`/`DELETE`. `hyalos github check <owner/repo>` mints a read-only token, shows it worked and revokes it. Tests: `core/hyalos/tests/github_app.rs` with a stand-in GitHub on loopback and a test-only key in `tests/fixtures`. Procedure: `docs/operations/github-app.md`. GitLab is not built.
- Gates (ADR-0020): `hyalos_policy::ask` returns an `Outcome`, never a `Result`, and only an on-time allow proceeds; `Engine::rule_gate` writes an unknown answer, the job ending held and the hold as one transaction, and replay refuses a log where unknown did not hold. Reasons are `ReasonCode`s (short codes), never free text.
- Backup and restore (ADR-0021): `hyalos log backup <new-file>` and `hyalos log restore <backup>` copy the log with SQLite (safe while the engine runs, never a plain file copy), verify the copy against the operator's public key, and only then create the destination, which must not exist. A restore never overwrites a log.
- The engine's keys (ADR-0022): `hyalos init` creates `engine.key` (mode 0600) and `engine.pub` from OS entropy, only when there is neither a key nor a log; a log with no key is a lost key and is refused, never replaced. The deterministic crates never see entropy. Operator procedures are in `docs/operations/`. Owner (ADR-0030): `keys::load` and `keys::prepare` also refuse a key file or config directory whose owner is not the effective user running the engine (`rustix`, a safe wrapper, in the `hyalos` crate only), whatever its mode. Core dumps (same ADR): `hardening::no_core_dumps` runs first in `main`, sets `RLIMIT_CORE` to 0/0 and on Linux marks the process not dumpable (a zero limit alone leaves a piped crash handler to decide), and the command stops if it fails; `LimitCORE=0` is no longer needed.
- Simulation lives in `crates/sim`: `Sim::new(seed)` gives a fake clock and one named random stream per boundary.
- The simulated world (ADR-0036): `crates/world` (not core, never linked into the binary) has a fake forge, fake model provider, `SeededSubstrate` and `SeededGate`, each on its own `Sim` stream and the fake clock, and `run_job(seed, dir)`, which drives one job through the real engine, policy, `mint_manifest`, broker `Admission` and `rule_gate`, then checks the state invariants, that a replay equals the state and that the log verifies. `Fixtures::for_seed` plants a forge token, provider key, job credential, raw forge content and raw model text, and `scan(dir, &fixtures)` looks for each as raw bytes in every file beside the database (S1.1). The `Forge` and `Model` traits live in the crate until the broker has real adapters. The runner stands in for the sandbox's calls and the broker's handling of them, because the sandbox-facing socket is not built.
- The broker never depends on the engine, log or substrate crates, and the engine never depends on the broker. `cargo xtask layout` enforces this; a new `core/` crate means editing its table and the ADR.
