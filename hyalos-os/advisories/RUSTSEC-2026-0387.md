# RUSTSEC-2026-0387: `crypto-bigint` 0.5.5 timing

**Outcome:** the exception in `deny.toml` stays. Within the scope below, the notary's secrets do not reach any branch that depends on their value. A `verifier-v*` release may proceed.

**Assessed:** 2026-11-24, at commit `c3480ec`, with rustc 1.99.1 (`rust-toolchain.toml`), `opt-level = 3`, for x86-64 Linux.

## The advisory

RUSTSEC-2026-0387 names secret-dependent branches in subtraction, zero counting, division and Montgomery multiplication, plus `UintRef` equality and `BoxedMontyForm::invert`. It lists only `>= 0.7.6` as patched, so `cargo deny` flags every earlier version. The fixes landed in crypto-bigint PRs 1311, 1355, 1358 and 1360, all on the 0.7 line:

- `UintRef` and `BoxedMontyForm` do not exist in 0.5.5.
- PR 1358 removed a branch from an AArch64 workaround in `primitives::borrowing_sub`, built on `overflowing_sub`. 0.5.5's `Limb::sbb` (`src/limb/sub.rs`) subtracts in a double-width word and shifts. It has no such workaround.
- PR 1360 covered zero counting, division, bit-length rounding and Montgomery multiplication. The notary's secrets never pass through 0.5.5's division, `inv_mod` or Montgomery code (below).

## What holds 0.5.5, and what holds a secret

`elliptic-curve` 0.13.8 holds 0.5.5, under `k256` 0.13.4, `p256` 0.13.2, `primeorder` 0.13.6 and `ecdsa` 0.16.9. These come from `tlsn` and `tlsn-attestation` at `v0.1.0-beta.1`, which is TLSNotary's newest release. Its `main` branch still locks 0.5.5. `mpz-fields` uses `crypto-bigint` 0.7.11, which is patched.

| Program | Secret it holds | Where the secret meets 0.5.5 |
|---|---|---|
| `notary` | Its secp256k1 signing key and each signature's nonce | `ecdsa::hazmat::sign_prehashed`. The nonce comes from RFC 6979, `k·G` from `k256`'s `mul_by_generator`, and `k⁻¹` from `k256`'s own addition chain. Scalars are added, subtracted and compared through `Uint::add_mod`, `sub_mod`, `sbb`, `ct_lt` and `conditional_select` |
| `notary` | Its p256 share of each TLS session's key exchange | `SecretKey::random`, `primeorder`'s point multiplication, and `p256`'s scalar and field arithmetic. The field uses `p256`'s own `fe_*` functions, and the scalar `multiply` uses `p256`'s own Barrett reduction |
| `attest` (prover) | Its share of the same key exchange | The same p256 paths |
| `hyalos-verify`, the monitor | None. They verify public signatures and public keys | `verify_prehashed`. Timing here can only reveal public values |

## The check

The release `notary` and the release `attest` prover were disassembled, and every conditional jump in their `crypto-bigint`, `elliptic-curve`, `k256`, `p256`, `primeorder`, `ecdsa` and `rfc6979` functions was listed with the instructions before it:

```
cargo build --release --locked -p attest --bins
objdump -d --no-show-raw-insn -C target/release/notary > notary.s
objdump -d --no-show-raw-insn -C target/release/attest > attest.s
python3 -I advisories/branches.py notary.s
python3 -I advisories/branches.py attest.s
```

In the notary, 99 functions were listed, and 34 have conditional jumps. In the prover, 68 were listed, and 19 have jumps. Each of the prover's 19 also appears in the notary's list with the same jumps, and it has no signing code. Each jump falls into one of these kinds:

| Kind | Where | Why it reveals no secret |
|---|---|---|
| A loop with a fixed count | `Scalar::invert` (56 squarings), `FieldElement::invert` and `sqrt` in both curves, the `Radix16Decomposition` loops, the window loops in `lincomb`, `mul_by_generator` and `primeorder`'s `mul` | The count is a constant |
| A public length, encoding or tag | `SecretKey::from_slice`'s length, SEC1 decoding, HMAC and SHA-256 block handling | Lengths and encodings are public |
| A validity result computed in constant time, then acted on | `from_slice`, `from_scalars`, `sign_prehashed`, `try_sign_prehashed_rfc6979`, `ScalarPrimitive::from` | The branch follows a `subtle` choice whose outcome is public: the key is valid, the nonce is in range, and the signature is non-zero. RFC 6979 retries a nonce with probability about 2⁻¹²⁸ |
| Lazy setup | `once_cell` around the generator's lookup table | It runs once, on public data |
| Variable-time by design | `invert_vartime` in both curves, `lincomb`, `verify_prehashed` | They are called only from signature verification, on public values. `lincomb` is also reached from `k256`'s variable-base multiplication, which only `Secp256k1EthSigner::new` calls, and the notary does not use that signer |
| 0.7.11's own code | `SafeGcdInverter`, `random_mod_vartime_core` | This is the patched version |

One branch was added by the compiler from 0.5.5's code. `Uint::neg_mod` masks its result by whether the input is zero, and in `k256`'s `Scalar::neg` that mask became a jump on the input being zero. In the notary, `Scalar::neg` is called only by `Signature::normalize_s`, on `s`, which the signature then publishes. Inlined into `lincomb`, the same test runs on the two halves of a decomposed scalar, but only during verification.

In both programs, the signing key, the nonce and the p256 share reach no conditional jump that depends on their value.

## What this does not cover

- **Other builds.** Only this toolchain, profile and target were checked. A compiler can turn a mask into a branch, as it did in `neg_mod`. `attest/tests/advisories.rs` fails if a version this assessment depends on changes, so the check is repeated.
- **Timing without branches.** Memory access patterns were checked only in source. `LookupTable::select` reads every entry. Instruction latency was not measured.
- **Code outside the curves.** SHA-256, HMAC and the MPC protocol's own arithmetic in `mpz` were not part of this advisory.
- **A formal proof.** This is a reading of the compiled code, not a `cargo checkct` or `dudect` result.

## When to redo it

When `attest/tests/advisories.rs` fails: a different `crypto-bigint`, `elliptic-curve`, `k256`, `p256`, `primeorder` or `ecdsa`, a different toolchain, or a new crate that depends on `crypto-bigint` 0.5.5. Remove the exception once TLSNotary moves to `elliptic-curve` 0.14 and no crate holds a version below 0.7.6.
